# ผลตรวจปริญญานิพนธ์เทียบกับโปรเจค Wildfire LoRa

วันที่ตรวจ: 13 กันยายน 2569 (2026-09-13)

ไฟล์หลัก: [รวมทุกบทฉบับไม่สมบูรณ์.docx](C:/wildfire_lora/เล่มปริญญานิพนธ์/รวมทุกบทฉบับไม่สมบูรณ์.docx) — ตรวจข้อความ สมการ และตารางของบทที่ 1–5 เทียบกับโค้ดใน `C:\wildfire_lora` โดยใช้ [บทที่ 2_1.docx](<C:/wildfire_lora/เล่มปริญญานิพนธ์/บทที่ 2_1.docx>) เป็นข้อมูลประกอบเฉพาะบางรายการ

## ข้อสรุป

ภาพรวมของเล่มตรงกับระบบที่พัฒนา แต่ยังไม่ควรถือเป็นฉบับสมบูรณ์ มีทั้งข้อความที่คลาดจากโค้ดปัจจุบัน รายละเอียดที่ขัดกันเอง และผลทดลองที่ยังไม่พอให้ตรวจสอบข้อสรุปได้ โดยเฉพาะวิธีนับความสำเร็จของ LoRa และการวัดกระแสไฟฟ้า

ส่วนที่อธิบายได้ตรง ได้แก่ Sensor Node หลัก 2 ตัว (NODE01/NODE02), SHT31, Sharp GP2Y1014AU0F, GPS, การสื่อสาร LoRa แบบจุดต่อจุดผ่าน Gateway, Backend ที่จัดเก็บข้อมูลใน MongoDB และเว็บ Dashboard แสดงข้อมูลและแผนที่ รวมถึงการใช้ Baseline และการประเมินจากหลักฐานหลายชนิด ส่วน NODE03 เป็นบอร์ดทดสอบระยะโดยส่งข้อมูลจำลอง ไม่ใช่โหนดเซนเซอร์หลักตัวที่สาม

ข้อสังเกตในรายงานแยกเป็น 3 ประเภท: **ยืนยันจากโค้ดได้**, **ต้องใช้หลักฐานทดลองหรือฮาร์ดแวร์ยืนยัน**, และ **ความครบถ้วนของเอกสาร** ไม่ได้ถือว่าผลทดลองที่ยังยืนยันไม่ได้เป็นผลเท็จ และไม่ได้แก้ตัวเลขให้ตรงกับสิ่งที่คาดเดา

### ขอบเขตและข้อจำกัดของการตรวจ

- ใช้โค้ดปัจจุบันเป็นฐานเปรียบเทียบ ไม่ได้ตรวจว่าแต่ละบอร์ดแฟลชเฟิร์มแวร์รุ่นใดอยู่จริง หากการทดลองใช้รุ่นก่อน ต้องระบุรุ่นและพารามิเตอร์ของการทดลองนั้น ไม่เปลี่ยนประวัติการทดลองให้กลายเป็นรุ่นปัจจุบัน
- ไม่ได้ทดลองภาคสนาม วัดไฟ หรือสอบเทียบเซนเซอร์ใหม่ การทำงานที่พบในโค้ดไม่ใช่หลักฐานว่าการทดลองฮาร์ดแวร์ผ่านแล้ว
- ยังไม่ยืนยันรูปแบบหน้ากระดาษ การตัดหน้า และความอ่านง่ายของภาพทั้งหมด เพราะเครื่องมือเรนเดอร์ Word ขาด LibreOffice จึงอ้างตำแหน่งด้วยบท ตาราง และข้อความค้นหาแทนเลขหน้า
- ไม่ได้ตรวจสอบแหล่งอ้างอิงวิชาการทั้ง 31 รายการอย่างครบถ้วน
- ไม่ได้แก้ไฟล์ Word หรือโค้ดต้นฉบับ สร้างเฉพาะรายงานนี้

## 1. จุดที่ควรแก้ก่อนเป็นอันดับแรก

### R01 — ค่า SF และเวลารอ ACK ไม่ตรงกัน

**ตำแหน่ง:** บทที่ 1 ขอบเขตด้านการสื่อสาร; บทที่ 3 ย่อหน้า “หลังส่งข้อมูล Sensor Node…” และย่อหน้าเริ่มอธิบาย NODE03; ตารางที่ 3.15

บทที่ 1 ระบุ SF7 แต่โค้ด NODE01, NODE02, NODE03 และ Gateway ปัจจุบันใช้ **SF12** ส่วนเวลารอ ACK ที่บางย่อหน้าระบุ **1.8 วินาที** ไม่ตรงกับโค้ดปัจจุบันที่กำหนด **6 วินาที** และไม่ตรงกับย่อหน้าถัดมา/ตารางที่ 3.15 ในเล่มเอง

ค่าปัจจุบันคือ 433 MHz, SF12, BW 125 kHz, CR 4/5, Sync Word 0x34 และกำลังส่ง 20 dBm การส่งข้อมูลเซนเซอร์มีได้สูงสุด **3 ครั้งรวมครั้งแรก** ไม่ใช่ส่งครั้งแรกแล้วส่งซ้ำอีก 3 ครั้ง

**แนวทางแก้:** ใช้ค่าชุดเดียวกันในส่วนอธิบายระบบปัจจุบัน และแยกตารางพารามิเตอร์ของการทดลองแต่ละรุ่นถ้าเคยใช้ต่างกัน คำว่า “ส่งซ้ำสูงสุด 3 ครั้ง” ควรเปลี่ยนเป็น “ส่งสูงสุด 3 ครั้งต่อหนึ่งรอบ โดยรวมการส่งครั้งแรก”

### R02 — ตารางขา GPS เขียนทิศทางรับ–ส่งกลับด้าน

**ตำแหน่ง:** ตารางที่ 3.5 แถว GPS NEO-6M

ข้อความปัจจุบันคือ `TX | TX GPIO34 | รับคำสั่งจากบอร์ด` แต่โค้ดกำหนด `GPS_RX_PIN = 34` และ `GPS_TX_PIN = -1` จึงเป็นการรับข้อมูลจาก GPS เข้าบอร์ด ไม่ใช่ส่งคำสั่งออกทาง GPIO34

**แก้เป็น:** `GPS NEO-6M | TX | GPIO34 (UART RX ของ ESP32) | รับข้อมูลตำแหน่งจาก GPS เข้าสู่ ESP32`

โค้ดชุดนี้ไม่ได้กำหนดขา UART TX สำหรับส่งคำสั่งไป GPS และ GPIO34 ของ ESP32 เป็นขารับเข้าเท่านั้น ทั้งนี้ ชื่อสัญญาณ TX บนโมดูล GPS กับชื่อหน้าที่ RX ฝั่ง ESP32 ต้องแยกกันให้ชัด

หลักฐาน: [การกำหนดขา GPS](C:/wildfire_lora/sensor_node/config.h:112), [การเปิด UART](C:/wildfire_lora/sensor_node/sensor_node.ino:1144), [เอกสาร ESP32 ของ Espressif](https://www.espressif.com/sites/default/files/documentation/esp32_datasheet_en.pdf)

### R03 — เปอร์เซ็นต์ความสำเร็จ LoRa ยังตรวจสอบย้อนกลับไม่ได้

**ตำแหน่ง:** บทที่ 3 ส่วนทดสอบระยะและตารางที่ 3.16; บทที่ 4 ตารางที่ 4.8; บทที่ 5 สรุปและอภิปรายผล LoRa

มีความไม่สอดคล้องหลายชั้น:

- ตารางที่ 3.16 ระบุ 3 รอบต่อระยะ แต่ข้อความบทที่ 3 และบทที่ 4 ระบุ 30 ครั้ง
- ข้อความบทที่ 4 ระบุ L01–L04 แต่ตารางมี L01–L05
- คำอธิบายมีทั้งพื้นที่มี/ไม่มีสิ่งกีดขวาง พื้นที่เมืองและชานเมือง และข้อความว่าทดลองในพื้นที่ไม่มีสิ่งกีดขวาง ต้องบอกสภาพเส้นทางจริงให้ตรงกัน
- ตารางที่ 4.8 ระบุ 98% ที่ระยะ 1.1–3.0 กม. และ 95% ที่ 4.1 กม. แต่ไม่มีจำนวนรอบสำเร็จ/จำนวนรอบทั้งหมดของแต่ละระยะให้ตรวจสอบ

ถ้าทดสอบระยะละ 30 รอบจริง อัตราสำเร็จจะเปลี่ยนทีละประมาณ 3.33 จุดเปอร์เซ็นต์ เช่น 29/30 = 96.67% และ 28/30 = 93.33% จึงไม่ได้ 98% หรือ 95% จากการนับแบบง่ายนี้ หากใช้ค่าบนจอ NODE03 โค้ดแสดงผลเป็นจำนวนเต็มแบบตัดเศษ และคำนวณจากยอดสะสมตั้งแต่เปิดบอร์ด: 29/30 จะแสดง 96 ไม่ใช่ 98

ตัวนับ `completedCycles` และ `acknowledgedCycles` ไม่ได้รีเซตอัตโนมัติเมื่อย้ายระยะ ดังนั้นค่าบนจออาจเป็นยอดรวมหลายระยะ ถ้าไม่ได้เริ่มตัวนับใหม่หรือบันทึกค่าตัวนับก่อน–หลังแต่ละช่วง

**ต้องตรวจจากบันทึกจริงก่อนแก้ตัวเลข:** ระยะละกี่รอบ, ได้ ACK กี่รอบ, ส่งจริงทั้งหมดกี่ครั้งเมื่อรวม retry, รีเซตบอร์ดหรือตัวนับเมื่อใด และ SUCCESS ในตารางได้มาจากแหล่งใด หาก 3 หมายถึงจำนวนครั้งส่งสูงสุดต่อรอบ ไม่ใช่จำนวนรอบทดลอง ต้องย้ายไปคอลัมน์พารามิเตอร์ retry

ยังไม่ควรยืนยันข้อสรุป “ผ่านเกณฑ์ 90%” จากตารางนี้จนกว่าจะยืนยันตัวเศษและตัวส่วนได้ ห้ามแทน 98/95 ด้วยค่าที่คำนวณเดาโดยไม่มีจำนวนสำเร็จจริง

หลักฐาน: [ตัวนับ NODE03](C:/wildfire_lora/sensor_node_3_range_test/sensor_node_3_range_test.ino:30), [สูตร SUCCESS](C:/wildfire_lora/sensor_node_3_range_test/sensor_node_3_range_test.ino:88), [การนับรอบทดลอง](C:/wildfire_lora/sensor_node_3_range_test/sensor_node_3_range_test.ino:328)

### R04 — ต้องแยก ACK, การรับข้อมูลที่ Gateway และการบันทึกฐานข้อมูล

**ตำแหน่ง:** คำจำกัดความผลทดลอง LoRa และการอธิบายเส้นทางข้อมูลในบทที่ 3–5

โค้ด Gateway ส่ง ACK ก่อนนำข้อมูลเข้าคิว HTTP ดังนั้น **ได้รับ ACK ไม่ได้แปลว่าบันทึก MongoDB สำเร็จแล้ว** อัตราได้รับ ACK ต่อรอบหลัง retry ก็ไม่ใช่ PDR ของการส่งวิทยุแต่ละครั้งโดยอัตโนมัติ

หากค่า RSSI/SNR ในตารางที่ 4.8 นำมาจากจอ NODE03 ค่านั้นวัดจากแพ็กเก็ต **ACK ที่ NODE03 รับ** ไม่ใช่จากแพ็กเก็ตขาขึ้นที่ Gateway รับ ส่วน Gateway มีการวัด RSSI/SNR ขาขึ้นแยกต่างหาก ต้องระบุฝั่งและวิธีสรุปค่า เช่น ค่าสุดท้าย ค่าเฉลี่ย หรือช่วงค่า

กรณี L05 หากหลักฐานมีเพียงไม่พบ ACK หลังส่งครบ ควรเขียน “ไม่ได้รับ ACK ภายในเงื่อนไขทดสอบ” ไม่สรุปว่า Gateway ไม่ได้รับสัญญาณเลย เว้นแต่มีบันทึก Gateway สนับสนุน

หลักฐาน: [ลำดับรับและ ACK ที่ Gateway](C:/wildfire_lora/gateway/gateway.ino:1026), [RSSI/SNR จาก ACK ที่ NODE03](C:/wildfire_lora/sensor_node_3_range_test/sensor_node_3_range_test.ino:264)

### R05 — ค่ากระแส 0.2 mA ทุกสถานะต้องตรวจวิธีวัดใหม่

**ตำแหน่ง:** ตารางที่ 4.11 รายการ PW07 และตารางที่ 4.12

ทั้งสองโหนดระบุอ่านเซนเซอร์ 0.2 mA, ส่ง LoRa 0.2 mA และ Deep Sleep 0.2 mA เท่ากันทั้งหมด ข้อมูลนี้น่าสงสัยหากหมายถึงกระแสของทั้งโหนดขณะทำงานจริง เนื่องจาก ESP32 ขณะ CPU ทำงานมีการใช้กระแสระดับหลายสิบ mA ตามเงื่อนไขในเอกสารผู้ผลิต ยังไม่รวมโหลดทั้งหมดของบอร์ดและวิทยุ จึงควรตรวจหน่วย ช่วงวัด จุดต่อมิเตอร์ และการจับช่วงส่งสั้น ๆ ก่อนใช้ค่านี้คำนวณพลังงาน ไม่ได้หมายความว่าทราบค่ากระแสจริงของต้นแบบแล้ว ([Espressif ESP32 Datasheet](https://www.espressif.com/sites/default/files/documentation/esp32_datasheet_en.pdf))

**ต้องเพิ่มหลักฐาน:** รุ่น/ช่วงวัดเครื่องมือ, วัดที่ขั้วแบตเตอรี่หรือราง 5 V หรือเฉพาะอุปกรณ์, แรงดัน ณ จุดวัด, วิธีวัดค่าเฉลี่ย/ค่าสูงสุด, สถานะ GPS และระยะเวลาแต่ละสถานะ อย่าเปลี่ยน 0.2 mA เป็น 0.2 A หรือ 200 mA โดยเดา

PW02 ระบุกระแสชาร์จ 1 mA และแรงดันเปลี่ยน 3.82 → 3.91 V แต่ไม่บอกระยะเวลาชาร์จและเงื่อนไขแสงเพียงพอให้ประเมินกำลังชาร์จ ตารางที่ 4.12 ยังไม่มีข้อมูลครบ จึงยังยืนยันระยะใช้งานแบตเตอรี่หรือสมดุลพลังงานรายวันไม่ได้

### R06 — แผงโซลาร์ 5 W/15 W ต้องยืนยันจากอุปกรณ์จริง

**ตำแหน่ง:** บทที่ 1–2 ระบุ 6 V 5 W; บทที่ 3–4 รวมถึงตารางที่ 3.6 ระบุ 6 V 15 W; บทที่ 5 ยอมรับความขัดแย้งนี้

โค้ดไม่สามารถยืนยันกำลังพิกัดแผงที่ติดตั้งจริงได้ และค่าที่เขียนใน README ก็ไม่ใช่หลักฐานของแผงที่ใช้ทดลอง ควรตรวจฉลาก รูปอุปกรณ์ หรือรายการจัดซื้อ แล้วใช้ค่าเดียวกันใน BOM วงจร วิธีทดลอง และการคำนวณพลังงาน หากเปลี่ยนแผงระหว่างรุ่น ให้ระบุว่าผลทดลองชุดใดใช้แผงใด

ข้อขัดแย้งของเอกสารควรแก้ให้จบ ไม่เก็บไว้เป็น “ข้อจำกัดงานวิจัย” ในเล่มฉบับสมบูรณ์

## 2. การอธิบายระบบที่ต้องปรับให้ตรงโค้ด

### R07 — โหมดทดสอบกับการสร้าง Baseline ต้องสัมพันธ์กับผลจริง

**ตำแหน่ง:** บทที่ 3 ส่วนทดสอบ Sensor Node และตรรกะความเสี่ยง; ตารางที่ 4.5 รายการ SN04

วิธีทดลองระบุใช้โหมดทดสอบ แต่ผล SN04 ระบุ Baseline 12 รอบ ใช้เวลาประมาณ 9 นาที โค้ดปัจจุบันกำหนด `TEST_MODE=1` ให้สะสมข้อมูลผ่านเกณฑ์ 5 รอบ ส่วน `TEST_MODE=0` ใช้ 12 รอบ จึงต้องระบุโหมดและรุ่นเฟิร์มแวร์ของผล SN04 ให้ชัด

ไม่ได้สรุปว่า “9 นาทีผิด” เพราะเวลาจริงรวมเวลาทำงาน การรอ ACK การส่งซ้ำ และรอบที่ค่าไม่ผ่านเกณฑ์ ไม่ใช่เพียงจำนวนรอบคูณเวลารอ รอบที่ใช้เรียนรู้เป็นรอบที่ผ่านเกณฑ์สะสม ไม่ได้กำหนดว่าต้องเป็นรอบผ่านเกณฑ์ติดต่อกันทั้งหมด

### R08 — USB Serial, ชื่อฟิลด์ HTTP และแพ็กเก็ต GPS ต้องอธิบายใหม่

**ตำแหน่ง:** บทที่ 1 ขอบเขตการสื่อสาร; บทที่ 2 หัวข้อ JSON; บทที่ 3 ภาพรวมระบบ; บทที่ 4 ส่วนการทำงาน Sensor Node

- เล่มอ้างว่า Backend รับได้ทั้ง Wi-Fi/HTTP และ USB Serial ผ่านคอมพิวเตอร์ แต่ไม่พบเส้นทาง USB Serial → Backend หรือโปรแกรม bridge ในโค้ดปัจจุบัน พบ Serial สำหรับติดตาม/วินิจฉัยการทำงาน หากเคยมี bridge แยก ต้องระบุไฟล์และวิธีใช้ มิฉะนั้นไม่ควรนับเป็นช่องทางนำเข้าของระบบที่ส่งมอบ
- Gateway ไม่ได้เปลี่ยนชื่อฟิลด์ย่อทั้งหมดเป็นชื่อเต็มก่อนส่ง HTTP แต่รับ JSON ย่อแล้วเพิ่ม `rssi` และ `snr` ส่วนการจัดเก็บ/ตอบ API ของ Backend ใช้ฟิลด์ที่มีความหมายชัดเจนขึ้น
- ข้อความบทที่ 4 ที่บอกแพ็กเก็ตตรวจวัดประกอบด้วยพิกัดด้วย ควรแยกเป็นแพ็กเก็ตตรวจวัด `t:"s"` (หรือ `t:"c"` เมื่อ CRITICAL) และแพ็กเก็ตตำแหน่ง `t:"gps"` พิกัดไม่ได้แนบอยู่ในทุกแพ็กเก็ตตรวจวัด

### R09 — ต้องแยกการประเมินของ Sensor Node กับ Backend

**ตำแหน่ง:** บทที่ 2–3 ส่วนตรรกะความเสี่ยง; ตารางที่ 3.13, 3.14 และตารางที่ 4.6–4.7

ระบบมีการประเมินสองชั้น แต่ไม่ได้ใช้สูตรเหมือนกันทั้งหมด Sensor Node ส่ง `st`/`c` ของตนเอง ขณะที่ Backend ใช้ `evaluateRisk` ประเมินซ้ำจากข้อมูลและประวัติ แล้วจัดเก็บ `node_state`, `node_confidence`, `server_state` แยกกัน ค่า `state` ที่บันทึกใช้ฝั่งเซิร์ฟเวอร์

ตัวอย่างจากการเรียกฟังก์ชัน Backend โดยตรงแบบไม่ใช้ประวัติ: แพ็กเก็ตที่ระบุ `st:"WARNING", c:57, sm:550, sr:450, at:34, ar:4, h:60, hr:0, sh:"OK"` ได้ผลฝั่งเซิร์ฟเวอร์ **WATCH คะแนน 53** เพราะคะแนนควันและความร้อนของ Backend เป็น 35 + 18 ขณะที่คะแนนหลักฐานสองกลุ่มดังกล่าวใน Node เป็น 32 + 25 ตัวอย่างนี้เป็นการตรวจฟังก์ชัน ไม่ใช่ผลทดลองฮาร์ดแวร์

**แนวทางแก้:** อธิบายเกณฑ์สองชั้นแยกกัน และเพิ่มคอลัมน์ผล Node/ผล Backend/ผลหน้าเว็บในกรณีที่ตรวจครบเส้นทาง ไม่กำหนดว่าทุกชั้นต้องมีชื่อสถานะเหมือนกันเสมอ ส่วนคะแนน 0–100 ควรเรียกคะแนนตามกฎ ไม่ใช้แทนความน่าจะเป็นเกิดไฟที่ผ่านการสอบเทียบ

การปิดเหตุการณ์ก็ไม่ใช่รอ NORMAL ใหม่อีก 3 ครั้งที่ Backend เสมอไป โค้ดยอมปิดเมื่อ Node และ Server ยืนยัน NORMAL ตรงกัน หรือผ่านเงื่อนไข NORMAL ต่อเนื่องฝั่ง Backend ตามทางเลือกในโค้ด ต้องแยกจากกลไกลดสถานะของเฟิร์มแวร์

### R10 — ตาราง threshold ต้องเก็บ AND/OR และข้อจำกัดการตรวจเซนเซอร์ไว้

**ตำแหน่ง:** ตารางที่ 3.13 และคำอธิบาย SENSOR_FAULT/อัตราการเปลี่ยนแปลง

ค่าตัดสินรายตัวไม่เพียงพอจะอธิบายพฤติกรรมทั้งหมด ตัวอย่างหลักฐานควันระดับ WATCH ของ Node ใช้ `(เพิ่มจากรอบก่อนอย่างน้อย 40 raw และอัตราอย่างน้อย 300 raw/นาที)` **หรือ** `(เพิ่มจาก Baseline อย่างน้อย 150 raw และค่าปัจจุบันอย่างน้อย 250 raw)` ไม่ใช่ raw ≥ 250 อย่างเดียว เกณฑ์อัตราอุณหภูมิและความชื้นก็มีเงื่อนไขขนาดการเปลี่ยนแปลงขั้นต่ำประกอบ

เวลา Δt ในโหมดภาคสนามใช้ช่วงเวลาที่คาดไว้ตามการตั้งค่าการทำงาน ไม่ใช่เวลาจริงครบทั้งรอบ จึงควรระบุว่าอัตราที่ใช้ในเฟิร์มแวร์เป็นค่าประมาณ หากจะอธิบายเชิงการวัดอย่างละเอียด

Sharp ส่งค่า ADC raw ไม่ใช่ค่า PM2.5 หรือความเข้มข้นควันที่สอบเทียบแล้ว และการตรวจ `sharpOk` ปัจจุบันดูเพียงว่าอยู่ในช่วง 0–4095 จึงยังไม่ได้ตรวจพบการถอดสาย/ค้างค่าทุกกรณี ค่า 0 หรือ 4095 ยังอยู่ในช่วงผ่านการตรวจนี้ อย่ารวมผลทดสอบถอด SHT31 เป็นหลักฐานว่าตรวจความเสียหายของเซนเซอร์ทุกชนิดได้แล้ว

### R13 — ตารางผลหลายชุดยังเป็นแบบฟอร์ม ไม่ใช่ผลที่ยืนยันแล้ว

**ตำแหน่ง:** บทที่ 4 โดยเฉพาะตารางที่ 4.6, 4.7, 4.9, 4.10 และ 4.12 รวมถึงบางรายการในตารางที่ 4.11

ยังมี `[กรอก]`, ช่องว่าง และ “ผ่าน/ไม่ผ่าน” ที่ไม่ได้เลือก รวมถึงวันที่/สถานที่ทดลอง จึงยังไม่พอให้ตรวจสอบการประเมินความเสี่ยง การฟื้นกลับสู่ NORMAL เส้นทาง Gateway–Backend–ฐานข้อมูล Dashboard และพลังงานครบถ้วน

ตารางที่ 4.6 มี 7 ประเภทกรณี × 2 โหนด = 14 แถวผล คำสรุป “ทั้งหมด 7 กรณี” ไม่จำเป็นต้องผิดถ้าหมายถึงประเภท แต่ต้องนิยามตัวส่วนให้ชัดว่าคิดจำนวนผ่านจาก 7 ประเภทหรือ 14 การทดสอบโหนด

ในตารางที่ 4.5 NODE02 ยังไม่ได้ยืนยันการตอบสนองควันแบบเดียวกับ NODE01 ตามข้อมูลที่กรอกอยู่ จึงไม่ควรสรุปว่าทดสอบควันครบทั้งสองโหนดแล้ว ช่วงอุณหภูมิ/ความชื้นที่อ่านได้ยืนยันการอ่านค่าในเงื่อนไขทดสอบ ไม่ใช่ความแม่นยำเชิงสอบเทียบหากไม่มีเครื่องมืออ้างอิงและการคำนวณความคลาดเคลื่อน

บทที่ 5 มีการยอมรับข้อจำกัดของหลักฐานอยู่แล้ว ซึ่งควรคงไว้จนกว่าจะทดลองครบ แต่ข้อสรุปเชิงตัวเลขต้องอ้างเฉพาะผลที่มีวิธีนับและหลักฐานรองรับ

### R14 — ไม่พบรายการบรรณานุกรมในเนื้อหาไฟล์รวมที่ตรวจ

### การสื่อสารและ ACK

> ระบบกำหนดการสื่อสาร LoRa ที่ความถี่ 433 MHz โดยใช้ Spreading Factor 12, Bandwidth 125 kHz, Coding Rate 4/5 และ Sync Word 0x34 ตรงกันทั้งโหนดและเกตเวย์ หลังส่งข้อมูลตรวจวัด โหนดเปิดช่วงรับ ACK และคำสั่งเป็นเวลาไม่เกิน 6 วินาทีต่อการส่งหนึ่งครั้ง หากไม่ได้รับ ACK ที่ตรงกับข้อมูลชุดนั้น จะส่งข้อมูลชุดเดิมซ้ำ โดยส่งสูงสุด 3 ครั้งรวมครั้งแรก การได้รับ ACK ยืนยันการรับข้อมูลที่เกตเวย์ในระดับการสื่อสาร LoRa ไม่ใช่การยืนยันว่าฐานข้อมูลส่วนกลางบันทึกสำเร็จแล้ว

### เส้นทางข้อมูล

> Sensor Node ส่งข้อมูลตรวจวัดและผลประเมินเบื้องต้นในแพ็กเก็ต JSON แบบย่อ ส่วนข้อมูลตำแหน่งส่งในแพ็กเก็ต GPS แยกต่างหาก Gateway เพิ่มค่า RSSI และ SNR ของแพ็กเก็ตที่รับ แล้วส่งข้อมูลต่อไปยัง Backend ผ่าน HTTP ทางเครือข่าย Wi-Fi โดย Backend แปลงข้อมูลเข้าสู่โครงสร้างจัดเก็บ ประเมินความเสี่ยงส่วนกลาง และให้บริการข้อมูลแก่เว็บ Dashboard

### การประเมินสองชั้น

> ระบบประเมินความเสี่ยงสองระดับ ได้แก่ การประเมินบน Sensor Node จากค่าตรวจวัดและข้อมูลอ้างอิงของโหนด และการประเมินส่วนกลางที่ Backend ซึ่งใช้เกณฑ์และข้อมูลย้อนหลังประกอบ ระบบจัดเก็บผลของแต่ละระดับแยกกัน ดังนั้นผลประเมินจากโหนดและผลส่วนกลางอาจแตกต่างกันได้ การทดสอบจึงต้องระบุระดับที่ตรวจสอบและผลคาดหวังของระดับนั้นอย่างชัดเจน

## 5. หลักฐานที่ควรเตรียมก่อนแก้บทผลทดลอง

1. รุ่น/วันที่เฟิร์มแวร์และค่า config ที่ใช้กับแต่ละการทดลอง รวมถึง TEST_MODE, SF, ACK timeout และจำนวนครั้งส่งสูงสุด
2. บันทึก LoRa แยกรายระยะ: เวลาเริ่ม–จบ รอบทั้งหมด รอบได้ ACK จำนวนครั้งส่งรวม และตัวนับก่อน–หลัง พร้อมแหล่ง RSSI/SNR และรายละเอียดเส้นทาง/เสาอากาศ
3. ผลทดสอบความเสี่ยง NODE01/NODE02 พร้อมค่าตรวจวัด Baseline สถานะ Node สถานะ Backend ลำดับเวลา และหลักฐานการเปลี่ยนสถานะ
4. ฉลากแผงโซลาร์ วงจรจ่ายไฟจริง และบันทึกวัดแรงดัน/กระแส/เวลาต่อสถานะ พร้อมรายละเอียดเครื่องมือ
5. ผล Gateway–Backend, Dashboard, การทำงานต่อเนื่อง และรายการบรรณานุกรมฉบับรวม

เมื่อหลักฐานครบ ควรแก้ตามลำดับ: ข้อเท็จจริงของระบบ → วิธีทดลองและตัวส่วน → ตารางผล → บทสรุป/อภิปราย → ภาษาและรูปแบบหน้า
