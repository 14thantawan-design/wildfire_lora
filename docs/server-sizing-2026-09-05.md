# ประเมินขนาดเซิร์ฟเวอร์ ForestGuard — 5 กันยายน 2026

ข้อสรุปจากโค้ดและการทดลองในเครื่อง: สำหรับระบบต้นแบบ 2–3 Sensor Node, Gateway 1 ตัว และผู้เปิด Dashboard จำนวนไม่มาก ให้เริ่มที่ CPU เต็มอย่างน้อย 1 vCPU พร้อม RAM 2 GB โดยต้องควบคุมการใช้หน่วยความจำของ MongoDB; ขนาดแนะนำคือ 1–2 vCPU / RAM 4 GB / SSD 40–50 GB ส่วน Oracle A1 1 OCPU / RAM 6 GB เหมาะกับการเริ่มระบบนี้ หากมีเครื่องว่าง

Oracle E2.1.Micro RAM 1 GB เหมาะเป็นทางทดลองแบบมีข้อจำกัด ไม่แนะนำเป็นเครื่องหลักที่รวม API + MongoDB + Tunnel ด้วยโค้ดปัจจุบัน นี่เป็นข้อเสนอทางวิศวกรรม ไม่ใช่ผลทดสอบบน E2 หรือ A1 จริง และไม่ใช่จำนวนผู้ใช้สูงสุดที่รับประกัน

## ข้อมูลจริงที่ตรวจแบบอ่านอย่างเดียว

MongoDB ในเครื่องเวอร์ชัน 8.2.4 มี readings 1,235 รายการ ขนาด BSON เฉลี่ย 903 bytes/รายการ; พื้นที่ collection ที่จัดสรร 405,504 bytes และ index 790,528 bytes ข้อมูลจริงขนาดเล็กนี้ยังใช้ยืนยันการทำงานเมื่อสะสมข้อมูลนานไม่ได้

อ่านเฉพาะสถิติฐานข้อมูล ไม่คัดลอกข้อมูลเซนเซอร์จริงหรือกุญแจเข้าระบบลงชุดทดลอง

## การทดลองแยกจากระบบจริง

- Host: Windows, Intel Core i5-12500H, 12 physical cores / 16 logical processors; Node.js 24.11.1, MongoDB 8.2.4
- ใช้ mongod แยกบน 127.0.0.1:27018 และ API จากโค้ดจริงบน 127.0.0.1:4100 ไม่มีการใช้พอร์ต 4000 หรือเปลี่ยนฐานข้อมูลจริง
- ปิด Telegram ใน process ทดลอง ไม่โหลด `.env` ของระบบจริง; ใช้กุญแจจำลองเฉพาะการทดลอง
- จำกัด WiredTiger cache ที่ 0.25 GiB ซึ่งไม่ได้จำกัด RAM ทั้ง process และไม่ได้จำลองเครื่อง RAM 1 GB
- สร้างข้อมูล 3 Node ส่งทุก 10 นาทีเป็นเวลา 365 วัน รวม 157,680 รายการ มี schema และ indexes ของโปรเจกต์จริง
- เพิ่มข้อมูลใหม่ของทั้ง 3 Node ทุก 5 วินาทีระหว่างทดสอบ (โหลดเขียนมากกว่าสถานะ CRITICAL ตามรอบส่งปกติ) พร้อม Gateway poll ทุก 2 วินาที
- จำลองการ refresh API ตาม Dashboard ทุก 5 วินาที โดยจับเวลารวมของ API ทั้ง 6 รายการและใช้ timeout 4.5 วินาที
- ทดสอบ 4 สถานการณ์ สถานการณ์ละประมาณ 20 วินาที ไม่ได้วัดการวาดหน้าเว็บ, latency อินเทอร์เน็ต, TLS/Tunnel, Telegram จริง, cloud agent, จำนวน alerts/commands มาก, backup, cold-cache หรือการรันยาว 24 ชั่วโมง

รวม 496 คำขอ ไม่มีข้อผิดพลาด HTTP/timeout ในการทดลองนี้เท่านั้น p95 มีตัวอย่างน้อย โดยเฉพาะกรณี 4 รอบ จึงไม่ใช่สถิติ latency ระยะยาว กรณีหลายแท็บอาจเร็วกว่าแท็บเดียวจาก cache ที่อุ่นแล้ว ไม่ใช่ระบบเร็วขึ้นเมื่อผู้ใช้เพิ่ม

CPU คำนวณจาก CPU time ของ process Node + mongod หารเวลาทดลอง ไม่ใช่เปอร์เซ็นต์ CPU ของทั้งคอม และแปลงเป็นค่า OCPU บน Oracle โดยตรงไม่ได้ คอมทดสอบมีหลายคอร์และความเร็วต่างจาก VM

RAM วัด RSS/resident ทุกประมาณ 1 วินาที อาจพลาดยอดสั้น ๆ ผลรวมค่าสูงสุดราย process คือ 383–533 MiB โดยยอดของแต่ละ process อาจเกิดคนละเวลา ไม่รวม OS, filesystem cache, Cloudflare Tunnel และ Oracle agents ในเครื่องจริง cloudflared ที่เปิดอยู่มี working set ประมาณ 36 MiB ณ จุดตรวจ แต่ไม่ได้รวมในโหลดทดลอง

Range scan ตรวจเอกสาร 52,577 รายการของ Node เดียวเมื่ออ่านช่วง 1 ปี การมีผลลัพธ์ไม่เกิน 1,000 จุดไม่ได้ทำให้ต้นทุนอ่านเหลือ 1,000 รายการ

ผล build ผ่าน และ backend unit tests เดิมผ่าน 24/24 ข้อ Process ของชุดทดลองถูกหยุดหลังจบ ไม่ได้แก้ source code การทำงานจริง

## สเปกที่ประเมินว่าเหมาะ

| ตัวเลือก | การประเมินสำหรับรวมเว็บ + API + MongoDB |
|---|---|
| E2.1.Micro / RAM 1 GB | อาจเริ่มทำงานได้ แต่เหลือ RAM เผื่อน้อยและ CPU พื้นฐานต่ำ ไม่แนะนำสำหรับเปิดต่อเนื่องโดยไม่ปรับและทดสอบบน VM จริง |
| 1 full vCPU / RAM 2 GB | ขั้นต่ำเชิงปฏิบัติสำหรับจำนวน Node และผู้ใช้เล็กน้อย ต้องจำกัด MongoDB cache และติดตาม RAM/CPU |
| 1–2 full vCPU / RAM 4 GB | ขนาดแนะนำสำหรับเริ่มใช้งาน มีพื้นที่เผื่อ OS, cache, backup และ request ที่เข้าพร้อมกัน |
| Oracle A1 1 OCPU / RAM 6 GB | เหมาะกับระบบต้นแบบนี้ ไม่จำเป็นต้องมี 12 GB เพื่อเริ่ม แต่ยังต้องยืนยัน latency/ทรัพยากรบนเครื่องจริง |
| Oracle A1 2 OCPU / RAM 12 GB | มีเผื่อเพิ่ม เหมาะเมื่อได้โควตาว่าง แต่ไม่ได้แก้ต้นทุน query ที่เพิ่มตามประวัติแทนการปรับโค้ด |

Oracle ระบุ E2.1.Micro มี CPU พื้นฐาน 1/8 OCPU และ RAM 1 GB จึงไม่ควรถือว่าเทียบเท่า VM ที่ให้ CPU เต็มหนึ่งคอร์ แม้ UI จะแสดงตัวเลข OCPU เป็น 1

MongoDB มี WiredTiger cache และหน่วยความจำอื่นนอก cache รวมทั้ง OS filesystem cache ค่าตั้งต้นของ cache คือค่าที่มากกว่าระหว่าง 50% ของ (RAM - 1 GB) กับ 256 MB ต้องตั้งให้เหลือพื้นที่สำหรับ Node.js เมื่ออยู่เครื่องเดียวกัน ตัวอย่างจุดเริ่มต้นที่ต้องวัดอีกครั้ง: RAM 2 GB ตั้ง cache 0.25–0.5 GiB; RAM 4–6 GB ตั้ง cache 0.5–1 GiB ตามข้อมูลและงานจริง Swap ช่วยรองรับกรณีฉุกเฉินแต่ไม่ได้เพิ่มความเร็วหรือแทน RAM จริง

## ดิสก์และการเก็บข้อมูล

SSD ค่าเริ่มต้นราว 47–50 GB เพียงพอเริ่มโหมดภาคสนาม 2–3 Node ควรมีพื้นที่ว่างเผื่อระบบ, journal, logs และสำรองข้อมูล การเก็บ raw readings ไม่มีวันหมดอายุในโค้ดปัจจุบัน

ตัวอย่าง 3 Node / เดือน 30 วัน ใช้งบวางแผนประมาณ 2–4 kB ต่อ reading รวม indexes (เป็นค่าประเมินเผื่อ ไม่ใช่ขนาดดิสก์ที่วัดได้):

| รอบส่งสมมติตลอดเดือน | จำนวน readings/เดือน | งบพื้นที่ข้อมูล+index โดยประมาณ |
|---|---:|---:|
| NORMAL ทุก 10 นาที | 12,960 | 26–52 MB |
| CRITICAL ทุก 20 วินาทีตลอดเดือน | 388,800 | 0.78–1.56 GB |
| TEST ทุก 5 วินาทีตลอดเดือน | 1,555,200 | 3.11–6.22 GB |

ตารางไม่รวม backups, journal, logs และ OS; สถานการณ์ส่งถี่ตลอดเดือนเป็นขอบเขตเปรียบเทียบ ไม่ใช่การคาดว่าจะเกิดจริง ข้อมูลจำลอง 157,680 แถวใช้ storage+indexes ขณะวัดประมาณ 54 MiB เนื่องจาก compression และข้อมูลซ้ำเป็นแพตเทิร์น ไม่ควรใช้ตัวเลขนี้รับประกันข้อมูลจริงทุกแบบ

## สิ่งที่ควรจัดก่อนเปิดใช้งานต่อเนื่อง

1. Build React ที่เครื่องพัฒนาและส่งเฉพาะ production artifacts พร้อม Backend ไปเซิร์ฟเวอร์ ใช้ service manager ให้เปิดกลับหลัง reboot
2. ตั้ง MongoDB cache ให้เหมาะกับ RAM จริง และติดตาม RAM, CPU, disk และการตอบ API
3. ลดการคำนวณกราฟช่วงยาวซ้ำทุก 5 วินาที เช่น cache ผลชั่วคราวหรือทำข้อมูลสรุปตามช่วงเวลา จุดนี้ให้ผลมากกว่าการเพิ่ม RAM อย่างเดียว
4. กำหนดอายุประวัติ/การเก็บสรุปและ backup ตามความต้องการผู้ใช้ ยังไม่ได้ตั้ง TTL หรือลบข้อมูลจริง
5. บน VM จริงให้ MongoDB/API เข้าถึงเฉพาะในเครื่องตามแผน Cloudflare Tunnel และตรวจ SSH/firewall รวมทั้งทดสอบ Gateway ส่งข้อมูลจริงก่อนย้ายโดเมน

รายงานนี้เป็นการตรวจและประเมินขนาด ยังไม่ได้ดำเนินการปรับข้อ 1–5 หรือย้ายระบบขึ้น Cloud
